# tzimpact

**Your database has appointments that will silently show the wrong time.
tzimpact tells you exactly which rows, and why.**

When the IANA time zone database changes a zone's rules, timestamps you already
stored keep pointing at the same absolute instant — but that instant no longer
lands on the local wall-clock time the user picked. A 10:00 booking quietly
becomes an 11:00 booking. Nothing errors. Nothing logs.

This happens on a schedule now. In 2026 alone: British Columbia went permanent
−07 (tzdb 2026b), Alberta permanent −06 and Morocco permanent +00 (2026c), and
tzdb's own release notes say the Northwest Territories are expected to follow.

```console
$ tzimpact diff 2026b 2026c
5 zones changed for future instants (2026b -> 2026c):
  Africa/Casablanca            2026-09-20 .. open        +1h -> +0h (-1h, 11 windows)
  Africa/El_Aaiun              2026-09-20 .. open        +1h -> +0h (-1h, 11 windows)
  America/Edmonton             2026-11-01 .. 2036-03-09  -7h -> -6h (+1h, 10 windows)
  America/Yellowknife          2026-11-01 .. 2036-03-09  -7h -> -6h (+1h, 10 windows)
  Canada/Mountain              2026-11-01 .. 2036-03-09  -7h -> -6h (+1h, 10 windows)

$ tzimpact scan --from 2026b --to 2026c \
    --sqlite bookings.db --table appointments --utc-col starts_at --tz-col tz
appointments: 5,000 rows scanned
  1,008 rows affected (20.2%)
    Africa/Casablanca              735 rows   -1h
    America/Edmonton               273 rows   +1h
  earliest affected: row 3579 in Africa/Casablanca
    was 2026-09-20 07:13  ->  now 2026-09-20 06:13
```

## Why not just diff the zone files

`zdump -v` prints every transition since year −2147481748 and has no notion of
"what changed between two releases" or "which of my rows care".
[tz-diff](https://github.com/hygt/tz-diff) compares rules but not your data.
Postgres, Java and Python ship tzdata updates without telling you what they
invalidated.

## Exact, not sampled

Offsets can only change at an explicit TZif transition or at an instant
generated by the POSIX footer rule. tzimpact enumerates the union of both
releases' boundaries and compares offsets on each resulting interval, so a
change cannot be stepped over.

This matters: sampling every 6 hours reports Alberta as one continuous
2026-11-01 → 2028-02-27 window. That is **wrong**. 2026b still put Alberta on
DST, so the two releases agree every summer — the real answer is ten discrete
winter windows, which is what tzimpact reports (`test_alberta_difference_is_winter_only`).

## Trust anchor

`tests/test_golden.py` reproduces each release's own NEWS file:

| releases | tzimpact finds | NEWS says |
|---|---|---|
| 2025b → 2025c | nothing | "Several code changes for compatibility with FreeBSD" |
| 2025c → 2026a | Europe/Chisinau, Europe/Tiraspol | "Moldova has used EU transition times since 2022" |
| 2026a → 2026b | America/Vancouver, Canada/Pacific | "British Columbia moved to permanent −07" |
| 2026b → 2026c | Casablanca, El_Aaiun, Edmonton, Yellowknife, Canada/Mountain | "Alberta moved to permanent −06. Morocco moves to permanent +00" |

The parser is separately checked against Python's `zoneinfo` across 12 zones ×
120 instants spanning both hemispheres.

## Install

```bash
pip install tzimpact   # not yet published
zic --version          # required: tzimpact compiles releases with the system zic
```

## Scope

tzimpact **reads**. It never writes to your database — corrections are emitted
for you to review and apply. It analyses future instants only; the past is
already settled.
